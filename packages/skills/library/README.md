# library-lean

The user's own library of API toolkits, as one AnythingLLM agent skill. For a service, the agent reads its API's docs, asks the user for its key, which they paste into the library's own settings (the model never sees it), and saves a toolkit: where the API is, which keys it calls with, what the agent learned of it, and small JavaScript functions that call it. A function runs again on request, and runs other functions as a flow, even across services. Nothing knows any one service.

Functions run in QuickJS, compiled to WebAssembly, inside AnythingLLM's process: a function sees its input and `kit`, never a file, a key or AnythingLLM. `kit.http` reaches only its toolkit's hosts, through the fence (public addresses only), with its toolkit's keys added outside the script. `kit.crypto` hashes, makes random values and checks signatures, outside the sandbox; `kit.secret.sign` signs with a signing key kept in the vault, which the function names and never sees ([extensions and secrets](../../../docs/notes/skills/library/extensions-and-secrets.md)). `kit.ssh.exec` runs a command on one of its toolkit's targets, machines the user registers on the Library page (address, account, key and host key's fingerprint), and `kit.ssh.put` and `kit.ssh.get` move files to and from them over SFTP; a function names the target, never its address or key. Why QuickJS, and what was measured: [docs/notes/skills/library](../../../docs/notes/skills/library/README.md).

| Action | Does |
| --- | --- |
| `guide` | how the library works, by topic (`static/guide/`), and worked examples (`static/snippets/`) |
| `library` | the toolkits at a glance, or one (`service`) in full |
| `secret` | asks the user for a key (`site`, `label`), given in the skill's settings (`NEW_KEY`) or on the Vault; asked again, says whether it came; or asks for a target (`kind` ssh, `label`), registered on the Library page |
| `call` | one request to an API, with a key (`auth`), to read its docs, spec or answers |
| `save` | a toolkit, a function (compiled first) or both; `test` runs what was saved; `remove` |
| `run` | a function (`name`, `inputs`); a run again, or one going on in the background (`run_id`, `stop`) |

## Where it keeps things

| What | Where |
| --- | --- |
| Toolkits, functions (and their last 5 versions), what each keeps between runs, runs, the runs not shown yet (`unseen/`) | `library-lean/` in AnythingLLM's storage |
| Keys, signing keys and targets (with their private keys), and the pages' key | `vault-lean/vault.json`, encrypted, shared with the browser and Artifacts skills |
| A key the user pasted, until the next call takes it | the skill's `plugin.json` (`NEW_KEY`, `KEY_FOR`: the site it goes to), in plain text, as AnythingLLM keeps every setting |
| The Library page | `public/library-lean/` beside AnythingLLM's server: the page, its state (nothing secret); `library-lean/page.json` holds its token and secret, and the agent's requests for a key |
| The Vault | `public/vault-lean/`: the page every skill that keeps secrets serves, and its keys section (`<token>-keys.json`, nothing secret); `vault-lean/vault-page.json` holds its token and secret |
| Your own versions of the guide, snippets and prelude | `library-lean/static/`, at the same paths as `static/`: they win over the shipped ones |

## Using it

`anywherellm-suite install` puts it in, or import it from AnythingLLM's Community Hub (see the [README](../../../README.md)); then switch on Library under Agent Skills and ask the agent to connect a service. Its ANYTHINGLLM_URL, the address you open AnythingLLM at, is optional: with it, the links work from anywhere. `library` ends with two links. The Vault is your own view of every secret by name: the keys, the signing keys (which you make or import there), and the browser skill's logins and passkeys, which you delete there; you can also give a key there when the agent asks. The Library page is your view of the toolkits and runs; lock a toolkit there once you've read its functions, and nothing changes it until you unlock it (the agent never reaches the skills' pages, so only you can). A locked toolkit's keys and targets are then for locked toolkits only: the agent's `call` and its unlocked toolkits can't send with them. Leave AnythingLLM's own web-scraping agent tool off if AnythingLLM is at a public address: it isn't fenced. For an address on your own network (a NAS, a home server), add its host to `FENCE_ALLOW` in AnythingLLM's environment, or let its origin (scheme, host and port) through on the Vault, under Allowed addresses, which also lists the addresses refused lately; it can't be AnythingLLM's own address, one of this machine's own services, or a loopback address. A key goes over plain http only to a host in `FENCE_ALLOW` or an origin let through there.

Every service takes a key or a token (for GitHub, a fine-grained personal access token). When the agent asks for one, it writes the site into `KEY_FOR` under Library in Agent Skills: paste the key into `NEW_KEY` there, save, and say done. The library's next call, whatever it is, seals the key into the vault, marks the request met, and empties both fields; a value saved again from a settings page left open is only emptied. The key is in plain text in the skill's `plugin.json` from your save until that call, and never in the chat. The Vault is a second place to give it, where the pages work. The pages' key is found or made by the skill (`PAGE_KEY`, see the [README](../../../README.md#install)). OAuth sign-ins were taken out to keep the skill small: GitHub's by the device flow is on the branch `archive/oauth-signin`, and sign-ins with a client of your own (Google, Microsoft, Slack...) on `archive/generic-oauth`.

A run the chat waited 40 s for goes on in the background: its end is sent to your ntfy topic (set `NTFY_URL`, and `NTFY_TOKEN` if the topic needs one, under Library in Agent Skills; nothing is sent without it; it says only that a run ended and how, never which function or its result, and everyone who follows the topic gets it), shown on the Library page, and at the top of the agent's next `library` or `run` answer. To run a function on a schedule, ask the agent ("every morning at 7, ..."): it adds an AnythingLLM scheduled job with the tool `@@library-lean` (guide topic `schedules`), which you see and change under Scheduled Jobs.

For a target, the agent asks with `secret` (`kind` ssh) and you register the machine on the Library page's Targets tab: its host, port and account, and the fingerprint of its host key, read on the machine (`ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub`). The page makes a key and shows the line for the account's `~/.ssh/authorized_keys`, or takes yours. A private address, or a port this machine forwards to the target (reached from a container as `host.containers.internal:<port>`), needs "On my network" ticked; scheduled jobs use a target only with "May run unattended". Choosing and hardening the machine is yours: a dedicated account without sudo, nothing secret on it.

A target mustn't be this machine, and mustn't reach this AnythingLLM, whose pages carry their secret. `anywherellm-suite install` on the host records the host's SSH host-key fingerprints and its own addresses in `<storage>/anywherellm-suite/this-host.json`; the skill refuses a target that shows one of those keys or sits at one of those addresses (or loopback, link-local, any address the container sees), at save and again when it connects, however it is ticked. Without that file, unreadable or without a host key, it refuses every target and says to run the installer (`health` reports it missing or out of date). Every time you save or try a target, the skill puts a one-time file in AnythingLLM's public folder and asks the machine, with one fixed command (curl or wget), to fetch it from `ANYTHINGLLM_URL` and from each of this host's recorded addresses on ports 3001, 443 and 8467, all at once; it also looks at whether it can see the vault's folder or is this machine's account (same hostname and user). A machine that fetches the file is refused, with the address and port on its card. It also warns when AnythingLLM has no password or the vault's key is kept beside the vault. This is a heuristic: it can't see a mount of the storage at another path or an address and port not listed, a machine that is compromised can answer falsely, and a firewall change afterwards isn't noticed until the next try. For a VM, keep it out of reach in the network too: the tailnet's access rules deny the VM's tag any port of this host; the VM's egress (a firewall on the VM, or the host's) denies this host's tailnet and LAN addresses; AnythingLLM listens on 127.0.0.1 where it can.

The Library page and the Vault carry a secret in their HTML, so a machine the agent can run commands on (a target) must not be handed their links. By default the agent's answers (`library`, `secret`, `target`) include them. `anywherellm-suite pages --hide` on the AnythingLLM host makes the file `<storage>/anywherellm-suite/page-links-hidden`: with it the answers say only where you open the pages, the browser's tab page shows no Vault button, and the agent is told never to ask for or fetch a link; `pages --show` removes it. The skills write both pages' root-relative paths in `<storage>/anywherellm-suite/page-links.json` (mode 0600: a path there is a way into the page, so never log it) whichever way the switch is, for the bridge and for `anywherellm-suite pages`, which prints the current links. The first page call after the switch is turned on replaces both pages' tokens and secrets once, so a link the agent has already seen stops working (old links and bookmarks 404). The apps and browser-tab pages are not touched.
