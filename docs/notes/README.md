## Layout and build

- **`docs/browser-tab.md` and `docs/page-links.md` are the file formats the phone app and the bridge read, and `tools/versions.env` is the image every check and the test lab use: data, not a package.** The phone app's bridge is its own repository (`~/dev/anywherellm-bridge`); it and the suite share only `page-links.json`, no code. The check that the two sides agree runs in `test-lab`, the one place that knows both. `docs/fence-lean.md` is the fence's own files, which nothing outside the suite reads.
- **One toolchain for the JavaScript parts,** at `packages/`: one `package.json`, `tsconfig.json`, lock and `build.mjs`, no npm workspaces. Node runs `.ts` itself (type stripping), so there is no `tsx`; `erasableSyntaxOnly` keeps the source strippable. The dev tools are `typescript`, `esbuild` and `@types/node@18`; the only other dependencies are the vendored libraries below.
- **Node 22.18+ to develop, Node 18 for what ships.** The image's Node is 18, so everything AnythingLLM runs, and the installer, targets `node18`. The API floor is Node 18's: `AbortSignal.any` (20.3) is out, and `target: node18` doesn't catch it.
- **ESM is chosen by extension.** `packages/package.json` has no `"type"`, so `.js` and `.ts` are CommonJS, which the skills need (AnythingLLM `require`s them); whatever is ESM is `.mts` (shared helpers, tests and the installer) or `.mjs` (`build.mjs`). A `"type": "module"` anywhere above a skill, or in a nested `package.json`, breaks the CommonJS fixtures.
- **Parts share the contract and the tooling, never modules.** `packages/shared/` is dependency-free source that esbuild bundles into each part (`#shared/...`, mapped by `package.json`'s `imports`), so a fix in it reaches a part only when that part is rebuilt. `build.mjs` fails a bundle that takes in a file from outside its own `src/` and `shared/`. The installer carries the skills as built text, not as imports.
- **Vendored dependencies are named.** `build.mjs`'s `VENDORED` lists what a part may bundle, pinned exactly in `package.json`: QuickJS for the library, `puppeteer-core` for the browser (the newest that runs on Node 18), `fast-json-patch` and `acorn` (the page check's parser) for apps. "No dependencies shipped" means nothing is installed beside a part. `STUBBED` bundles Puppeteer's browser-download, proxy, archive and BiDi modules as empty ones, which is most of its size; a pattern that matches nothing fails the build, so an update that moves a module is caught.
- **A skill's `static/` is text inlined into its `handler.js`** (`STATIC_FILES`), because the Hub's upload and install's payload take text. A file at the same path under `<storage>/<hubId>/static/` wins at run time, so guides, snippets, parts and pages can be tuned on the live instance and a reinstall doesn't undo it. Only text and code that runs inside QuickJS or a page is static; what touches secrets or the network stays in TypeScript.
- **Skill tests run against the built bundle** (what AnythingLLM loads); a test that imports `src` directly uses `.ts` import paths. `tools/check` builds once and runs each part's `<part>:unit`. Fixtures and e2e scripts stay `.js`: they stand in for, or run inside, AnythingLLM's own JavaScript.
- **Checks.** `lefthook.yml` calls the scripts in `tools/`, and `make` only wraps them. CI runs the type-check, the tests and `tools/e2e` on Linux, the one platform tested; `tools/e2e` and `tools/e2e-skill` need a container and are not hooks. `tools/versions.env` pins the one AnythingLLM image every check uses. Mode-600 checks are skipped on Windows, which has no modes (the code and these checks stay for whoever runs it there).
- **Evals live in `~/dev/test-lab`:** they are slow, cost model calls and vary between runs. It installs a suite commit with that commit's `tools/install`, from a worktree, so `main` can move during a run.

## What AnythingLLM gives us

- **A stdio MCP server gets AnythingLLM's own environment** (`server/utils/MCP/hypervisor`): `AUTH_TOKEN`, `SERVER_PORT` and `STORAGE_DIR` reach an MCP server in a container and on Desktop alike (the bridge's control server uses them), so the servers file (`plugins/anythingllm_mcp_servers.json`) holds no secret. AnythingLLM listens on `SERVER_PORT`, else 3001. An entry is `command`/`args`/`env`, or `url` with `type` `sse`, `streamable` or `http` (`streamableHttp` is refused); single tools can be switched off with `anythingllm.suppressedTools`.
- **Desktop has no password or multi-user mode,** and only Linux with podman has run on real hardware (the root README's table says the rest).
- **A skill's `handler.js` is loaded afresh for each agent run,** so state that must outlive a call is kept on `globalThis` (`perProcess`), and a cache that depends on the build goes through `perBuild`.
- **A skill has no time limit.** A scheduled job has one (`SCHEDULED_JOB_TIMEOUT_MS`, AnythingLLM's 5 minutes by default), runs in a child AnythingLLM forks with no workspace, only the tools it names and approval granted, and names a skill `@@<hubId>` (an MCP server `@@mcp_<name>`), which is why the bridge's control server's `schedule` takes `@` in a tool id. `jobTimeLeft()` is that child's own budget. The built-in `create-scheduled-job` tool asks the user's approval in the chat and works in single-user mode only. A job also runs on demand, as its Run now button does: `POST /api/scheduled-jobs/<id>/trigger` (internal API, a login's token), also when the job is switched off (tools/e2e checks both); the wake skill uses it. AnythingLLM loads a skill's handler.js only for an agent run (utils/agents/index.js), never at startup, so what a skill runs between calls starts at the first agent run after a restart.
- **AnythingLLM keeps a skill's settings and on/off switch in its `plugin.json`** and writes it again when a setting changes, so install keeps `active`, each `setup_args` value and the description's `Saved now:` part when it updates a skill, and `health` compares JSON by value. Its settings page saves the whole `plugin.json` as it showed it (`updatePluginConfig` with the skill's config, merged at the top level), so a page left open writes back every value it showed: a skill that writes its own settings (`shared/settings.mts`) can't trust a value to stay emptied.
- **Internals are a last resort:** supported surfaces first. What the pages still lean on is the public folder they are served from and the collector's `custom-documents/raw-*.json` files their events are read from. Making the pages' key with `models/browserExtensionApiKey` was tried and dropped on 2026-10-30 (below, "Keys from the Hub").

## Installer

- **The agent's control server is anywherellm-bridge's** (moved 2026-10-20; its notes have why, and the decisions that came with it: no MCP SDK, roles, the runtime, install being polite to the servers file). The suite's `install` therefore writes the skills only, and no servers-file entry.
- **`Told` is the one error to show as it is** (`#shared/errors`): a skill's own refusals and the installer's extend it, so a catch tells them from a bug.
- **The installer remembers nothing.** `--storage DIR` on every command, else Desktop's, else refuse: with one instance to install into, remembering earned less than a settings file costs. `uninstall` never removes a skill's data.
- **The pages' key came from install** (`--page-key brx-...`) from 2026-10-18 to 2026-10-30, one key the user made for every skill's pages; since then the user gives it in a skill's `PAGE_KEY` setting, and `--page-key` is optional (below, "Keys from the Hub"). It isn't moved to `/api/v1`, whose upload takes only a developer key, which can do everything and can't sit in a public page.

## Shared infrastructure

- **The fence** (`shared/fence.mts`, `net.mts`; its files: [docs/fence-lean.md](../fence-lean.md)): a skill reaches the public web only. Private ranges are one `net.BlockList`; a request is checked at the skill's own lookup and again for each redirect hop, and connections are pooled a few seconds per allow-list. The user's own network is let through by `FENCE_ALLOW` (hand-written hosts, any port) or on the Vault's Allowed addresses.
  - **One origin at a time** (scheme, host and port), never the host's other ports: approving a service on one port had let every skill reach AnythingLLM and the bridge on the same name. A key goes over plain http only to a `FENCE_ALLOW` host or an origin let through. The Vault refuses a public origin, any loopback one (in AnythingLLM's container that's the container's own server and collector; give the machine's network name instead) and the suite's own services (AnythingLLM's address, this machine's addresses on 3001, 443, 8467 and AnythingLLM's port), and refuses what it can't tell.
  - **A refusal is at once, in words that send the user to the Vault** (`letThrough`, then `FENCED`: don't reach it another way), and is noted in `refused.json`, which the Vault offers with an Allow button. Asking again after the user let it through is the intended path.
  - **Caches depend on the build:** a reinstall once left a running AnythingLLM reading the hosts' entry an earlier build kept under the same `perProcess` key, so every fenced library call failed until the file changed. A cache now goes through `perBuild`, keyed by `SHARED_STAMP` (a hash of `shared/`'s sources); `perProcess` is for what holds something live (a browser, a timer, a queue).
- **2026-10-21: the fence's asks are gone; the Vault lets an address through.** A chat through AnythingLLM's developer API used to wait up to 2 minutes for the user's once, always or deny, which AnywhereLLM Lite asked for and the bridge wrote into `fence-lean/asks/`, with a run scope (`AsyncLocalStorage`, grants, `outsideRun`) carried through every skill for it. Why: the bridge and each skill must install and work alone, and without the bridge nobody could answer an ask; AnythingLLM's own `requestToolApproval` approves wherever it has no channel to ask on, and whitelists per skill, not per origin, so it can't stand in. The Allowed addresses section is shared code (`shared/addresses.mts`) that the browser and the library each serve, so it works with either alone. The bridge now only reads `page-links.json` ([docs/page-links.md](../page-links.md)).
- **Atomic files** (`shared/atomic.mts`): a write goes to a temp file and renames; `updateJson` takes a lock folder beside the file across processes (a scheduled job is a process of its own), re-reads inside it and breaks a stale lock. `readJson` takes only a missing file for empty, so a damaged file is never written over.
- **The vault** (`shared/vault.mts`, `logins.mts`) is one encrypted file for the instance, `<storage>/vault-lean/vault.json`, changed under that lock. Work that needs the network (a token's renewal) is done before the change, which checks that what it read is still there. A test with two processes writing at once loses nothing and fails without the lock.
  - **Its format is a contract** (`FORMAT`, 2 since 2026-10-30): the skills release apart (a Hub import updates one) and meet in this file, so a skill refuses a newer format than its own, which writing again would lose fields of, and upgrades an older one at its next change (`UPGRADES`). Not a migration shim: the upgrade is how a newer format keeps a store that skills released before it still share.
  - **The key** is random, made once and kept beside the vault (`vault-lean/vault.key`), so a copy of the storage could open the vault. It is not derived from AnythingLLM's `SIG_KEY` and `SIG_SALT`: those are AnythingLLM's to change, and a change would close the vault for good. `VAULT_KEY_FILE` takes the place of the file beside the vault, which is moved out (setup in the root README's [Secrets](../../README.md#secrets)); it belongs in AnythingLLM's environment, not its `.env`, which AnythingLLM writes again with only the keys it knows. A key is made only when nothing is sealed yet (no `vault.json`, no sealed file): a vault whose key is gone stays closed rather than being given a new key.
  - **Cookies are a sealed file per workspace** beside the vault (`vault-lean/sealed/`), so a cookie save rewrites neither the vault nor every process's cached copy.
  - **Not a security boundary:** the skills run in AnythingLLM's process and open the vault with the same key. A stronger step needs an OS boundary, a container.
- **The Vault page** (`shared/vault-page.mts`, `vault.html`) is shared code each skill that keeps secrets bundles, so each stands alone. A Vault skill of its own and merging library with browser were both set aside: a skill can't call another, the browser needs a Chrome and the library doesn't, and one tool of about 20 actions routes worse than two. Each skill writes and applies its own section (logins, keys), and both the shared Allowed addresses; the page shows a tab for each it finds (Keys, Logins, Addresses: since 2026-10-22 API keys and signing keys are groups on Keys, each heading with its count, and the tabs carry none, so the bar fits a phone), and a module `VERSION` stops an older skill writing over a newer page.
  - **Open:** the tab state carries the Vault's link (`docs/browser-tab.md`), so anyone with a tab's link reaches the Vault; and the library's page watch stops 30 minutes after the page was shown, so a delete on a Vault opened later waits for the next library call.
- **Pages** (`shared/pages.mts`): a skill's pages go into AnythingLLM's public folder, served without a sign-in. A page posts what the user does through the browser-extension upload with the `brx-` key, which can add and embed documents, list workspaces and revoke itself, never read a chat or a document. The collector writes each post to a file the skill takes oldest first, claimed by renaming, so only one process applies an event. Posts are applied while a page is open and drained before every call, in turns per event title, so a call reads a page after what was posted; the agent learns what the user did from its next read, not from a queue of notes, which any context could consume. A page's link is a capability URL carrying a secret its events repeat; `rotate` removes the old files.
  - **A public path can't leave the public folder** (`publicPath`), and every write, removal, listing and rename there goes through it. No posted value is turned into a path: an earlier `oauth-code` event, taken without a secret because the provider's redirect page had none, once let anyone with the pages' key remove any file AnythingLLM could write, the vault included. That flow is gone (see Library).
- **Text the agent reads is data, never instructions.** `shared/answer.mts` checks the requests the agent writes (it never sets a credential header; a key goes in from the vault), hides every secret in what comes back, and clips long answers, giving a long JSON answer its outline.
- **Same-origin pages, recorded, not fixed.** Every page is model-written script served on AnythingLLM's own origin, so in a browser signed in to AnythingLLM it could read the web UI's token and call its API. The fix is a trusted shell holding the page in a sandboxed iframe, posting and polling over `postMessage`.

## Library

Why QuickJS, what was measured and the limits: [skills/library](skills/library/README.md).

- **The sandbox contract:** a function runs in QuickJS (WebAssembly) in AnythingLLM's process and sees its input and `kit`, never a file, a key or AnythingLLM. `kit.http` reaches only its toolkit's hosts, through the fence, with the toolkit's keys added outside the script and hidden everywhere; `kit.run` runs a flow and shares the run's deadline, request budget and log; `kit.state` is kept when a run ends well. The sandbox goes no further once the deadline or a stop has decided a run.
- **`policy.ts`'s `check` is the one place to refuse:** when a function is saved, a run starts and each request is made, from a function or the agent's own `call`. It allows everything while the user tests; approval and read-only keys would go there.
- **Secrets are given in the skill's own settings (`NEW_KEY`, since 2026-10-30) or on the Vault page, never on AnythingLLM's question card:** once answered, the card shows the answer as plain text in the live chat whatever its `inputType`. The page's fields ask for a new password (`autocomplete="new-password"`, random names) so Chrome fills in no saved login, and what's typed is sealed on the device with the vault's public key. A key is limited to 60 calls a minute, per process (`credentialed`). A toolkit keeps only its extra hosts; the base address's are derived, so changing a base address doesn't leave the old host reachable.
- **The description lists what is saved** (`listing.ts`, refreshed after `save`): a model that can't see the library's contents goes to a web search, and AnythingLLM reads `plugin.json` again for each agent run.
- **Runs outlive the chat.** A chat waits `LIBRARY_WAIT_MS`, then answers with the run's id and leaves it going in AnythingLLM's process (up to `LIBRARY_RUN_MS`); `run_id` waits again and `stop` stops it. Each run is a file of its own, `running` at its start and `interrupted` once its process is gone or it is a minute past its deadline. The end leads the next `library` or `run` answer and shows on the Library page's Runs tab (the notice over ntfy went on 2026-10-31: below), tracked by one `unseen/` marker per run so a chat and a job never write the same file; a job's run that fails keeps its marker for the next chat.
- **A scheduled job never goes to the background:** it gets the job's time left less a margin for the agent's report, and a run is refused when too little is left. Scheduling is AnythingLLM's own `create-scheduled-job` with `tools: ["@@library-lean"]` (guide topic `schedules`).
- **No OAuth sign-ins; every service takes a key or a token on the Vault** (2026-10-22). Sign-ins with a client of the user's own (a redirect page, PKCE, and a definition the agent writes from a provider's docs, which a page it read may steer) were the heaviest and most exposed code in the skill, with four security fixes in a day; they are on `archive/generic-oauth`. GitHub's by the device flow followed: about 340 lines and a Vault group for one provider, used once, where a fine-grained personal access token does the same; Google's device flow doesn't grant Gmail's scopes, so it couldn't carry mail either. It is on `archive/oauth-signin` (`presets.ts`, `device.ts`, `oauth.ts`: a waiting code kept on its vault entry, a refresh token spent once). A vault entry of kind `oauth` is no longer read.

## Browser

Details: [skills/browser](skills/browser/README.md).

- **The skill decides what the model can't see:** a field behind a dialog, a date field's format, a submit the page keeps disabled and a code field that moved are handled in code, and it refuses what wouldn't work and says why. Secrets are entered on the tab's page only, sealed, and typed or set by the skill; the model never sees them.
- **A saved password is set, not typed** (`act.ts` `fillOn`): one call into the page checks that the field's window is the top one and is on the login's host, then sets the value through the input's own setter, since keystrokes go to whatever has the focus, which a page can move between keys. A code is typed after the same check. A page that ignores a set value is refused, and the user takes the tab over. The tab's picture hides a shown password: the read that marks a password field also gives it `-webkit-text-security: disc` for good.
- **A takeover is one hold:** the agent reads but `open`, `act`, `login` and `call` are refused, through one dispatcher check that also marks the tab busy, so a user's tap and an agent step never drive the tab together. A login saved, a password typed while holding and a passkey a site made then are all an `Offer`, saved once the page no longer asks for a password and is still on its site.
- **Passkeys:** every tab has Chrome's virtual authenticator holding the saved passkeys. Only the user adds one, while holding the tab; one made while the agent has it is taken out. Nothing else may connect to the skill's Chrome during a passkey case: even one DevTools message leaves the authenticator unanswered.
- **Cookies** are saved through the browser's own DevTools session after a step and as it closes, only when they changed. localStorage and IndexedDB aren't kept: a site that keeps its sign-in there signs in again with the saved login. Chrome's profile is a temporary folder removed in the background and with retries, because a throw from that handler would take AnythingLLM down.
- **Choices from the eval.** A check that a person is at the browser is the user's: act refuses to click one by its own name, and real reCAPTCHA, hCaptcha and Turnstile sit in cross-origin frames a read never sees, so the guide covers those. An identity provider's Allow for the asked sign-in is the agent's to press.

## Artifacts (the apps skill)

Details: [skills/apps](skills/apps/README.md).

- **hubId `apps-lean`,** ported from the lean edition (not the unmerged `apps-manager` branch: the apps manager was built afresh on 2026-10-22, below), on the shared helpers: a lock per app, the invocation's workspace, and the pages' key, public folder, event intake and folder watch. Its parts, topics and runtime are `static/`, tunable under `apps-lean/.static/` (a dot, so no workspace can be named like it).
- **A page's events reach only its own app:** each app has a secret in its page, and an event is applied only to the app whose secret it carries. The lean edition took the workspace and app an event named, so one page's link could change any workspace's apps.
- **The page check reads a page's scripts and runs none** (`apps/src/names.ts`, acorn): it parses each script and looks every name it reads up through its scopes. Until 2026-10-20 it ran them in `node:vm` in a worker thread, and vm is no security boundary: a page the model wrote could leave the context and run as AnythingLLM, with the storage and the vault key in reach. Reading misses a name made at run time in a way it can't see (`window[name] = ...`) and counts every assigned name as declared, so it is lenient where it can't tell.
- **A scheduled job may name a workspace** (the first skill to take one from the model) but is held to `list`, `read` and `do` on an app whose app.json says `"jobs": true`, which only a chat's `edit` sets; `delete` is refused in a job. Naming none, it works in its own `_jobs`, which chats don't see, so a `read` or `do` there on an app name that is the user's elsewhere is refused with the workspace to name: unnamed jobs had been refreshing a `_jobs` copy of the user's deck for days (board #13).

## Notebook and archived skills

- **Notebook** (`packages/skills/notebook`) is leaner than the memory skill on purpose: no embedder or vectors (a paraphrase can miss; the agent can try other words), no scopes, no two-call `apply`. If agents don't think to read it, the first thing to try is listing notes in the skill's description, as the library lists its functions.
- **Notebook's meaning comes from the model (2026-10-25, 0.2.0).** A memory bank ported from the old Python `memory` repository (Mem0, LlamaIndex, Qdrant, fastembed) was weighed, as an MCP and as a skill, and the notebook took its place. A skill ships on the Hub with no host-side config, and AnythingLLM gives a skill no embedder: the only ones are its server modules (what the memory skill used) and the developer API's `POST /v1/openai/embeddings`, which takes a key no other part needs. So read ranks by each word's rarity (BM25's IDF: a word most notes hold, like "user", counts for little; a note holds a word when one of its words starts with it, so "drink" finds "drinks" and "tea" not "steak"), the description asks the agent for the subject plus synonyms, related words and names, and a note carries optional `keywords` its text lacks. An empty `keywords` on edit keeps a note's, since models send empty values for parameters they don't use. If an eval of paraphrased questions shows misses, the next step is embeddings from that endpoint, the key a skill setting, merged into the same ranking.
- **Archived, not shipped:** the memory skill (it wrote into AnythingLLM's vector database through server modules, no real agent had called it, and AnythingLLM 1.16 has memory of its own). The SSH targets were archived with it on 2026-10-18 and came back on 2026-10-20, merged onto the Vault, the per-origin fence and locking (next section). If memory comes back: its facts in its own file, its vectors in a file of its own, embeddings from `POST /v1/openai/embeddings`, keyword search when no key is set. `install` doesn't remove a skill it no longer carries, and the live instance keeps its `memory-lean/` data.

## SSH targets for the library, and ssh2, 2026-10-17

- **What:** `kit.ssh.exec` runs a command on a target, a machine the user registers on the Library page's Targets tab (`src/targets.ts`): a vault entry of kind `ssh` with its host, port, login, private key (pasted without a passphrase, which would cost about 0.4 s of pure-JavaScript bcrypt on every connect and protects nothing the vault doesn't; or made there as ed25519, the page showing only the public line) and the SHA-256 fingerprint of its host key. A function names the target and nothing else (any other field is refused by name), and only a target its toolkit lists in `targets`. What the target is, and how it's hardened, is the user's: the library sees a host and a port.
- **Reaching it:** `shared/net.mts` gains `connect`, a fenced TCP connection (the same lookup and checks as `send`). A private address is reached only for a target the user ticked "On my network" (since 2026-10-31, whose address is private by itself: below, "The leaner Library page"), at its own host and port; FENCE_ALLOW plays no part, since it opens every port of a host to every skill. A port the host forwards is reached from the container as `host.containers.internal:<port>` (169.254.1.2 under pasta, a private address).
- **The second bundled dependency: ssh2 1.17.0,** with asn1, safer-buffer (MIT), bcrypt-pbkdf (BSD-3-Clause) and tweetnacl (Unlicense), pinned; `VENDORED` names their folders. The image has no `ssh`, and nothing is installed beside a part. Its optional native parts (`cpu-features`, its crypto binding) are left out of the bundle (`LEFT_OUT` in `build.mjs`: required inside a try, they fail and ssh2 uses `node:crypto` and its own wasm Poly1305), so the skill stays text and runs on any OS. `@microsoft/dev-tunnels-ssh` brings four packages and a tunnels-first API; writing the protocol is too much crypto to own. The risk: one maintainer.
- **Refused:** password and keyboard-interactive sign-in (only the key is given), agent forwarding and X11 (never asked for), any forwarding from a function (no kit call opens one), and channels the machine opens toward us (ssh2 refuses those it didn't ask for: tested with forwarded-tcpip and x11). A host key other than the pinned one ends the connection before sign-in.
- **Not this machine (2026-10-20):** a target may not be loopback, link-local, unspecified or an address of this machine, nor show this machine's SSH host key, however it was ticked (`shared/thishost.mts`). The container's own address list isn't enough (a pasta container doesn't list the host's tailnet address, and pasta carries the connection to the host's sshd), so install records the host's addresses and host-key fingerprints in `anywherellm-suite/this-host.json` and the library refuses them too, and every target while that file is missing or holds no key. An IPv6 address that carries a refused IPv4 one (mapped, compatible, NAT64, 6to4) is refused with it. Two registered targets are the same account when they show the same host key and login, or have the same canonical host, port and login; a locked toolkit's pins use the canonical host (`pinv` 2; pins of the first form are rewritten once on first open, kept as they were when their target has changed since).
- **Limits:** a command 30 s by default, 300 s at most and never past the run's end; 256 KB of each stream by default, 1 MB at most; 1 MB of stdin; 4 at once and 60 a minute per target per process; commands count in a run's 200 requests. A command past its time, or in a run that's stopped, gets TERM and its channel is closed 2 s later; `remote_may_run` says when the machine sent no exit status. ssh2's `stream.signal` sends nothing once stdin is ended, so TERM goes through its protocol object (`term` in `targets.ts`; the pin keeps that stable).
- **Files (phase 2):** `kit.ssh.put` and `kit.ssh.get` over SFTP (`client.sftp`), at most 1 MB a call, paged with `append` and `offset`/`bytes`. A put writes `<path>.part-<random>` and moves it over the path with `posix-rename@openssh.com`, so a reader never sees half a file and a failed one leaves nothing; a server without that extension (ssh2's own, which the unit tests use) gets a plain rename, or a remove and then a rename, and if that last step fails the new content stays in its part file. One write and one read a call: ssh2 splits them into requests the server takes (254 KB for OpenSSH); `get` answers text when the page is valid UTF-8, else base64, with the page's sha256. A transfer has no TERM: when its time runs out or the run stops, its connection is ended. Paths are the account's own (a relative one, or `~/`, from its home); the machine's permissions are the only jail.

- **Left as they are, from the /simplify pass:** a connection per command (one kept per run would save handshakes; later, with the job phase), the vendored code unminified (about 280 KB more than minified), one sidecar in `tools/e2e-skill`, the sign-in status kept in the vault entry.

## The leaner Library page, 2026-10-31

Shane chose it on 2026-10-31, from the Library Design canvas (page "Library", section 5, "A leaner Library: the same three tabs, less on each"), for a user who doesn't read code. `static/pages/library.html` and the page's side of `src/page.ts` were replaced; the House UI block is the same as every page's.

- **Three tabs, Toolkits, Machines and Runs, and two screens.** A toolkit's card names what it connects to (its hosts, or its machines) and its functions by what they do (the first sentence of the description, else the name). A function opens on its own screen with its last run (`store.lastRuns`: taken from the last 20 runs, which the Runs tab reads anyway, or else from the newest run file of that function, so it needn't be among them; a deleted toolkit's functions are never looked for) and its code behind "Show the code". Runs are the last 20 by day. Lock acts at once; Unlock, every Delete and Replace link ask first in a sheet (a `<dialog>`, which keeps focus inside); Delete sits behind ⋯. The page opens on Machines while the agent asks for one. "Targets" stays the agent's word and the code's (`kind: "ssh"`, `kit.ssh`, `targets.ts`, the `target-*` events), so stored targets keep working; what the user reads, and the chat's answer that sends them to the page, says machines.
- **One command sets a machine up.** The page needs the key before the save, so the skill keeps a spare: the page's key for the next machine, made the first time the page's state is written without one and kept sealed beside the vault (`library-ssh-spare`, #shared/vault writeSealed) until a save takes it. Each write of the state reads its public half from a per-process copy, opened again only when the sealed file's stamp changes. It isn't made at the first need (Add a machine opened, or the agent asking): the page draws the command from the state it has, and a key asked for by an event would leave the form without one until the next state. The command is run with `sh -c`, so any login shell reads it the same:
  `sh -c 'mkdir -p ~/.ssh && touch ~/.ssh/authorized_keys && chmod 700 ~/.ssh && chmod 600 ~/.ssh/authorized_keys && { grep -qF "<key>" ~/.ssh/authorized_keys || echo "restrict ssh-ed25519 <key> library-lean <name>" >> ~/.ssh/authorized_keys; } && ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub'`.
  Run twice it adds nothing: a line with that key, whatever its options or comment, is kept. The save says which key the command carried; one that is neither the machine's own (set up again at the same host, port and account) nor the spare is refused under the command ("used for another machine"), so two forms open at once can't both take one key. The skill reads the fingerprint from the pasted line (`SHA256:` and 43 characters) and refuses it under the field when there's none; the page checks only that nothing was left empty, and the skill's refusals say the rest. With "Use my own key instead" the command is only the `ssh-keygen` part.
- **The address tells a private one, in place of the "On my network" tick.** A target is let through the fence at its own host (`allow: [host]`) when its address is private by itself: a private IP, or a name that is this network's by its name alone (#shared/fence `privateByItself`, which `hostRefused` builds on for every request). A name that looks public is public: one that resolves to a private address is refused when it connects, as for any request, and the page says to give the address itself. The tick could only loosen: it let a public-looking name through to whatever private address it answered with, which can't happen now, and nothing the page posts says private (a `private` field is ignored). Nothing of it is kept on the target: the rule is applied to its address at each connect, so a target saved under the old tick follows it too. That is a tightening: a target saved ticked with a name that looks public but resolves privately is now refused when it connects, and is given again as its address. The checks that hold whatever the address (not this machine, its addresses or host key; not reaching AnythingLLM's pages or storage; the installer's record) are as they were.
- **What the page says.** A save's refusals are in the user's words, each with the field it concerns (`targets.ts` `Refused`, `result.field`), since only the page saves a target. A try says why it didn't sign in (`problem`: the key refused, another host key, this machine, a fenced address, no answer) and whether one is going (`trying`, from a save or Try again until it ends, never more than a minute; a Try again while one is going does nothing). A try that didn't sign in keeps its status, its problem and its end in one write, and only a problem it can name: none reads as "failed". The machine's card draws each, with its one next step.
- **Left out of the boards:** a function that hasn't run says so; "Not used" offers Try again (a firewall change or an unmount fixes it); a machine a locked toolkit keeps names it ("Kept for Build box, which is locked"); the syntax colours of the code boxes, three of the canvas's own per theme, since the pages use House UI's tokens only (`shared/themes.test.mts`).
- **Tested:** `tests/page.test.mts` and `tests/targets.test.mts` (the spare taken once and a stale one refused, each refusal's field, the address rule, the switch, the problems), the drift test now covering the machines' fields; the e2e runs the page's own command twice on OpenSSH 10 through a function, checks one line was added with 700 and 600, and adds a second machine from the line it printed, which signs in with the page's key though its line carries `restrict`. Checked in the image's Chrome at 390 and 320 px and at 200% text: no sideways scroll, no control under 44 px.

## NEW_KEY in a skill imported from the Hub, 2026-10-31

On the test instance (suite main e4ac68b, AnythingLLM 1.16 in podman) muse saw a key saved in `NEW_KEY` through Settings › Agent Skills reach the library only after a restart, and the field left full in `plugin.json` once the key was sealed, until emptied by hand.

- **Why:** AnythingLLM keeps an imported skill in `plugins/agent-skills/<folder>`, the folder its `plugin.json`'s hubId names, and an import from the Hub names both by the Hub's own id for the item (`utils/agents/imported.js` `importCommunityItemFromUrl`), not `library-lean`. `shared/settings.mts` found `plugin.json` by the skill's hubId, so for such a skill it found none. `setting` then read the call's runtimeArgs, which AnythingLLM reads from `plugin.json` once, as it loads the skill for an agent run (`utils/agents/index.js`, `ephemeral.js`: `loadPluginByHubId`, `parseCallOptions`), and a chat's agent session (its websocket, `endpoints/agentWebsocket.js`) keeps that run until it ends: a value saved meanwhile reached the skill only in a new session, as after a restart. `setSettings` found no file and wrote nothing, so the slot answered "NEW_KEY is empty again" with the key still there. A skill's `PAGE_KEY`, and the library's list in its description (`listing.ts`), went the same way.
- **Ruled out:** AnythingLLM requires a skill's `handler.js` afresh for each agent run (it deletes it from require's cache), and its settings save writes the whole `plugin.json` the page sends, in place (`updateImportedPlugin`), never from what the server holds; nothing in `settings.mts` or what it calls keeps a value per process (`perProcess`, `perBuild`). In the folder install puts it in, the slot already worked inside the server's process.
- **Fix:** `settings.mts` finds `plugin.json` beside the running `handler.js` when AnythingLLM loaded it from its skills folder, whatever the folder is named, and by the hubId only where the bundle runs elsewhere (a test); it reads the file at each call, never the runtimeArgs, as before. The slot says so if `NEW_KEY` couldn't be emptied.
- **Tested:** `shared/settings.test.mts` loads the module, bundled as the skills' build bundles it, from a folder named as a Hub import names one. `tools/e2e` has a stand-in model now: OpenAI's chat completions inside the container, which AnythingLLM's Generic OpenAI provider asks with native tool calling and streaming off (`PROVIDER_DISABLE_NATIVE_TOOL_CALLING`, `GENERIC_OPENAI_STREAMING_DISABLED`, set in `tools/e2e`), and which calls the tools a queue file names. An agent run through AnythingLLM's developer API (its own agent, in its own process) asks for the key, waits while the key is saved through the settings endpoint, then calls again: the key is taken and sealed, `NEW_KEY` is empty in `plugin.json` and as AnythingLLM lists it, and still empty after another run. Both with the skill where install puts it and in a folder (and hubId) `e2e0hubitem0id`, as a Hub import has it; without the fix the second fails at the run's next call, which reads `NEW_KEY` empty.
- **Still open:** a skill imported from the Hub is the agent's tool `@@<the Hub's id>`, not `@@library-lean`, which the schedules guide names for a scheduled job.

## House rules

- **No migration shims.** Code that only carries an earlier edition's data or config over is not kept: the only installed instance is the author's and is migrated once, by hand or by an uncommitted script, and the code then knows the new format only. A later user with older data would be given a one-off script outside the packages.
- **The name is AnywhereLLM Suite,** so it isn't mistaken for Mintplex Labs' AnythingLLM on sign-in consent screens and public pages. Names that refer to AnythingLLM itself (`ANYTHINGLLM_*`, `anythingllm_mcp_servers.json`), the skills' hubIds and folders (`*-lean`) are unchanged. No aliases for old names.
- **Linux is what's supported; Windows and macOS are nice to have.** CI, the "verified" claims and the installer's docs cover Linux only, and nothing is promised elsewhere. But don't cut those machines off on purpose or without reason: reach for generic, platform-agnostic tools (TypeScript and Node's own APIs, `path`, no shell-only or Linux-only tricks in `packages/`), keep the small platform branches that exist (`install/src/paths.mts`'s Desktop folders, `shared/atomic.mts`'s Windows lock retries) rather than deleting them, and add a Linux-only dependency only when it buys something real. If a Windows or macOS machine turns up that needs fixing, a fix is welcome; adding it back to CI is a decision of its own.
- **The apps manager (2026-10-22),** designed with AnywhereLLM Lite on the Browser Lean Design canvas (page "Apps manager"): one token page for every workspace's apps (`src/manager.ts`, `static/pages/manager.html`), in the Vault's look, opened from Lite's Apps row through the bridge's `/pages` (`apps`). It shares `apps-lean/` in the public folder with the apps' pages, so `tokenPage` gained a file-name `prefix` (`manager-`), which keeps its sweep and rotation off the apps' pages. Its events have their own title (`apps-lean-manage`): the apps' intake drops anything without a patch. New store steps: `retitle` (the title only; the name is the file and what the agent calls), `undoChange` (the newest data change, only while it is the line the page showed), `putBack` (an earlier file, keeping the one it replaces), `trashed` and `restore` (a new page address; refused while the name is taken). No icon set in this edition, so rows show the title's initial. Its watch, like the apps pages', starts at the skill's first call in AnythingLLM's process.
